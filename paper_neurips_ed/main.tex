\begin{abstract}
Tool-augmented LLM agents are increasingly proposed for scientific computation, but it remains unclear when tool access improves reliability and when the additional control loop introduces new errors. We study this question with PHREEQC, a deterministic geochemical simulator whose inputs, executions, outputs, and final answers can be inspected. We introduce \BenchName, an expert-validated benchmark with \BenchN{} multiple-choice items derived from \BenchScenarioN{} validated simulation scenarios, together with an agent harness for writing PHREEQC inputs, executing the simulator, inspecting outputs, and committing to a final answer. We evaluate direct answering, chain-of-thought prompting, and tool-augmented agents across model families and output-access protocols. Tool access produces net accuracy gains across all five top- and mid-tier completed agents, but at variable retention costs --- between 52.7\% and 87.8\% across model families --- so even when net-positive, agents lose items the same model answered correctly without tools. Chain-of-thought does not close the gap to grounded execution. Output-access protocol effects align with model capability tier rather than vendor: a metadata-guided interface preserves accuracy at large token savings for top-tier models (Opus, Sonnet, and GPT-5.4 all within $\pm$2.5\,pp of raw-output accuracy at 20--61\% input-token reduction), but produces an 8--10\,pp accuracy cost for mid-tier models in our evaluation (GPT-5.1 and GPT-5.2). The contribution is a benchmark and diagnostic evaluation package for studying tool-augmented scientific agents, not a new geochemical model or a claim that PHREEQC is solved.
\end{abstract}

\section{Introduction}

LLM agents are increasingly connected to external tools, including calculators, databases, code interpreters, theorem provers, and scientific software. Frameworks such as ReAct and Toolformer established tool use as a core language-model capability, and scientific systems such as ChemCrow and autonomous chemistry agents show that tools can extend model behavior beyond text-only prediction \citep{yao2023react,schick2023toolformer,bran2024chemcrow,boiko2023autonomous}. For scientific computation, however, the central evaluation question is not simply whether a model can call a tool. It is when tool augmentation improves a model's ability to operate a deterministic scientific workflow, and when the tool loop itself becomes a source of errors.

Deterministic scientific simulators make this question testable. Unlike open-ended scientific question answering, simulator tasks can provide executable evidence and reproducible ground truth. At the same time, they stress capabilities that common benchmarks can hide: domain-specific input synthesis, error recovery, context management for large outputs, numerical extraction, and final-answer calibration. A model can fail before the simulator runs, after a successful run, or while mapping correct numerical output to the requested answer. Evaluating only aggregate accuracy hides these distinctions. Output access is a particularly load-bearing variable: simulator outputs are heavy-tailed, ranging from a few kilobytes to nearly a megabyte, so the protocol the agent uses to inspect them shapes both context cost and the evidence it can actually see.

We study this evaluation problem through PHREEQC, a standard simulator for aqueous geochemistry \citep{parkhurst2013phreeqc,appelo2004geochemistry}. PHREEQC is deterministic, widely used, domain-specific, and text-output heavy. Its outputs contain section headers, tables, convergence diagnostics, and repeated time-step records, making it a realistic case for studying scientific-tool use without requiring reviewers to evaluate novelty in geochemistry.

We introduce \BenchName, a high-confidence benchmark of \BenchN{} multiple-choice question items derived from \BenchScenarioN{} validated simulation scenarios. Each item is answerable by constructing and executing a PHREEQC simulation and extracting a specific computed quantity. The benchmark uses multiple choice because it provides deterministic scalable grading, but every item is grounded in a unique simulator-derived target value. We therefore use the benchmark as a diagnostic harness for evaluating scientific agents, not as a geochemistry trivia set.

The empirical surprise is that simulator access is not a monotone intervention. Across the five top- and mid-tier completed agents, simulator access adds 61--108 new correct answers per model but also costs 9--31 items the same model previously got right, giving retention rates between 52.7\% and 87.8\%. This makes retention, gain/loss accounting, chain-of-thought controls, output-management ablations, trajectory metrics, and failure analysis central to the benchmark.

This paper asks five evaluation questions:
\begin{enumerate}[leftmargin=*, itemsep=2pt]
    \item When does simulator access improve LLM performance over direct and chain-of-thought baselines?
    \item When does tool use introduce regressions on items the same model can answer without tools?
    \item How do output-access protocols change accuracy, token cost, wall-clock time, and agent trajectories?
    \item How robust are the results to scenario dependence and answer-label imbalance?
    \item Where does the externally observable computation chain break: input construction, execution, output navigation, or answer mapping?
\end{enumerate}

Our contribution is an evaluation benchmark and analysis methodology, not a new geochemical model or a new agent architecture. We make five contributions:
\begin{enumerate}[leftmargin=*, itemsep=2pt]
    \item We provide \BenchName, an expert-validated benchmark and artifact package for evaluating LLM agents in a deterministic, unique-answer scientific software setting.
    \item We compare direct answering, chain-of-thought prompting, and grounded simulator execution to separate reasoning-only gains from tool-use gains.
    \item We use gain/loss/retention analysis to show that aggregate accuracy hides tool-induced regressions.
    \item We ablate TOC-guided versus raw-output access and report token, wall-clock, step, and PHREEQC-execution metrics.
    \item We report scenario-level, answer-label, trajectory, and failure analyses so the benchmark supports diagnosis rather than only ranking.
\end{enumerate}

\section{Related Work}

\paragraph{Tool-augmented language models.}
Prior work has studied agents that interleave language-model reasoning with actions or external calls \citep{yao2023react,schick2023toolformer}. Scientific tool-use systems demonstrate the promise of connecting LLMs to chemistry tools and laboratory or simulation workflows \citep{bran2024chemcrow,boiko2023autonomous}. Our focus is narrower and more diagnostic: rather than proposing a general autonomous scientist, we evaluate when simulator access improves or degrades performance under controlled grading.

\paragraph{Benchmarks for agentic systems.}
Agent benchmarks increasingly emphasize executable tasks, tool use, and failure analysis rather than static question answering. SWE-bench, for example, evaluates models on real software repair tasks with executable artifacts \citep{jimenez2024swebench}. Scientific-agent benchmarks such as ScienceAgentBench similarly evaluate generated programs, execution results, and costs \citep{chen2025scienceagentbench}. \BenchName{} follows the same broad philosophy for scientific computation: the task is not to recall a fact, but to operate a deterministic external system and produce a verifiable answer. Its distinctive role is to provide a PHREEQC-specific benchmark and artifact package with simulator inputs, outputs, trajectories, output-access ablations, and failure-analysis queues.

\paragraph{LLMs in scientific domains.}
LLM work in chemistry and geoscience often focuses on prediction, literature synthesis, or assistant-style workflows \citep{jablonka2024leveraging}. We instead use a scientific simulator as an evaluation harness. This changes the central question from whether a model knows domain facts to whether it can reliably synthesize inputs, run a deterministic tool, navigate outputs, and preserve correct behavior under tool augmentation.

\section{Benchmark and Agent Harness}
\label{sec:benchmark}

\subsection{Dataset and Task}

\BenchName{} contains \BenchN{} four-option multiple-choice items derived from \BenchScenarioN{} validated PHREEQC simulation scenarios authored and reviewed by domain experts in aqueous geochemistry, with topic ideas inspired by the official USGS PHREEQC example database and the phreeqcusers community forum. Each item has a unique simulator-derived target answer; the agent must write a PHREEQC input file, execute the simulator (PHREEQC 3.8.6 with an author-supplied validated \texttt{phreeqc.dat} thermodynamic database), inspect generated output files, and commit to its final answer by writing a file containing only the letter (A, B, C, or D); missing or unparseable final-answer files count as incorrect. LLMs exhibit answer-position preferences under one-shot prompting (Appendix~\ref{sec:appendix-label-behavior}); we therefore balanced the truth-label distribution to be approximately uniform: A=\BenchAlwaysA, B=\BenchAlwaysB, C=\BenchAlwaysC, D=\BenchAlwaysD. For the scenario-clustered analysis in Section~\ref{sec:scenario}, a scenario stem is operationally defined as the first paragraph of the problem statement after whitespace normalization.

\subsection{Scope and Choice of Simulator}

\BenchName{} tests three things: whether agents can translate a scientific task into simulator input, run the simulator, inspect output, and commit to a unique answer; whether tool access improves performance through grounded execution rather than only longer reasoning traces; and whether output-access choices affect cost and reliability for large simulator outputs. We use PHREEQC because it has the properties we want from a simulator testbed --- deterministic, used by real scientists, requires specialized input syntax, and produces verbose textual output with section headers, tables, and time-step records --- properties also shared by other command-line scientific tools such as groundwater, molecular-simulation, and electronic-structure software. We do not claim that PHREEQC itself is the scientific contribution, that geochemical modeling is solved by LLM agents, that tool access is always beneficial, that aggregate accuracy alone is sufficient to evaluate agents, that any single output-access protocol generalizes across domains, or that the measured retention rates and failure proportions transfer unchanged to other simulators.

\subsection{Tool Environment}
\label{sec:harness}

The custom agent is given four tools: \texttt{write\_file}, \texttt{read\_file}, \texttt{list\_file}, and \texttt{execute\_phreeqc}. Each question runs in an isolated workspace with a fixed maximum of 24 agent steps. PHREEQC execution is deterministic for a given input file and the frozen benchmark database. The agent is instructed to use tools for quantitative questions and to base the final answer on simulator output. This design intentionally keeps the harness simple: it is a controlled environment for comparing no-tool reasoning, reasoning-only prompting, and tool-augmented execution.

\subsection{Output-Access Protocols}
\label{sec:toc}

PHREEQC outputs are heavy-tailed rather than uniformly large. Among completed agent workspaces, \OutputLeHundredK{} of observed \texttt{result.out} files are at most 100k characters while \OutputGtHundredK{} exceed it; the median output is \OutputPFiftyChars, the 90th percentile is \OutputPNinetyChars, and the maximum is \OutputMaxChars. The distribution is in fact bimodal: the small mode tops out near 55k characters (95th percentile within the $\le$100k items), while every output above the cap begins at roughly 369k characters or higher. The 100k cap therefore sits in an empty interval between modes rather than within either mode, which makes Raw100k a natural baseline rather than an arbitrary truncation. Output access is therefore part of the evaluation rather than a neutral implementation detail: returning the full file can saturate context, while returning too little starves the agent of evidence it needs to extract the requested quantity. We treat output access as a controlled variable and study three protocols, each targeted at a different regime of the output-size distribution:

\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Agent-TOC} (size-agnostic; main agent condition). \texttt{execute\_phreeqc} returns execution status, file names, file sizes, stderr/stdout snippets, and a table of contents for \texttt{result.out}; the agent then issues \texttt{read\_file} calls with explicit line ranges. Context cost is bounded regardless of output size, so this protocol spans the full distribution, including the \OutputGtHundredK{} long tail.
    \item \textbf{Agent-Raw100k} (typical case). \texttt{execute\_phreeqc} returns \texttt{result.out} inline, truncated to \RawCapChars{} characters per execution by preserving the head and tail of the file. Because the cap is non-binding on \OutputLeHundredK{} of items, TOC versus Raw100k on these items reduces to a clean comparison between structured pointer access and full inline output, without confounding by truncation.
    \item \textbf{Agent-Raw500k} (long-tail stress). The same protocol with a \RawHighCapChars{}-character cap. This is targeted at the \RawCapAffectedN{} cap-binding items where Raw100k actually truncates, and asks whether residual errors on the long tail are explained by additional output evidence rather than by reasoning or extraction failures.
\end{itemize}

All three protocols share the agent loop and tool set; only the payload returned by \texttt{execute\_phreeqc} differs. We do not present TOC as a universal replacement for retrieval, summarization, or domain-specific parsers. It is one deterministic output-management mechanism for this evaluation harness --- return structure eagerly, defer content until requested --- and the comparison of interest is against budgeted raw access under the same simulator, task set, and agent loop.

\section{Main Results}
\label{sec:main-results}

All main experiments use the frozen \BenchName{} benchmark. Accuracy is computed as correct answers divided by all \BenchN{} items; ungraded answers count as incorrect. We also report token usage, latency, number of PHREEQC executions, failed PHREEQC executions, and step-limit behavior for agent runs. Sub-5\,pp accuracy differences should be read as within rerun variance and not as substantive protocol effects (Appendix~\ref{sec:appendix-stability}); larger gaps and directionally consistent patterns across models are the basis for substantive claims. Because closed-model APIs can drift, all results should be interpreted as measurements of the listed model endpoints at the time of the rerun rather than as permanent model properties.

Table~\ref{tab:main-results} reports direct, chain-of-thought, TOC-agent, and raw-agent accuracy where available. The chain-of-thought baseline addresses the concern that apparent gains might come from eliciting more explicit model reasoning, rather than from using PHREEQC as an external computational tool. Direct no-tool baselines sit in the \GPTFiveFourOneShot--\OpusOneShot{} range across model families, just above the \BenchMajority{} majority-label floor; this is the intended shape of the benchmark, since items that direct models could solve reliably from parametric knowledge were excluded during construction (Section~\ref{sec:benchmark}).

Chain-of-thought prompting yields roughly $\pm 8$pp around the direct baseline and is not consistently positive: Opus loses 4.0pp under CoT and GPT-5.1 loses 4.0pp, while Sonnet, GPT-5.4, and GPT-5.2 gain 6.0--8.0pp. Tool access then adds 15.0--42.5pp on top of the better of the two no-tool conditions for the five top- and mid-tier completed agents: Opus +42.5pp, Sonnet +42.5pp, GPT-5.4 +37.5pp, GPT-5.2 +19.0pp, and GPT-5.1 +15.0pp. Reasoning-only prompting therefore does not substitute for grounded simulator execution on this benchmark; the headline accuracy gains are attributable to tool use rather than to additional reasoning tokens.

Gemini 3 Flash Preview's TOC agent reverses this pattern, reaching only \GeminiThreeFlashTOC{} (47/200) --- a \GeminiThreeFlashTOCMinusBestNoTool{} regression below its better no-tool baseline (CoT, \GeminiThreeFlashCoT{}) and the only completed agent in our evaluation where tool access actively harms aggregate performance. The dominant failure mode is step-budget exhaustion without commitment: 117/200 trajectories exhausted the 24-step budget while continuing to issue tool calls and never produced a final-answer message, and an additional 33 trajectories committed to a final message that was not parseable in the required answer format. No trajectories failed due to API errors, rate limits, or billing constraints --- all 200 ran to completion under the same harness, prompts, step budget, and infrastructure as the other five models. Among the 50 trajectories that produced a parseable answer, 47 were correct (94.0\% conditional accuracy), indicating that the bottleneck is agent-loop control and final-answer commitment rather than reasoning or PHREEQC operation. We read this as a third capability tier --- below-mid --- where tool augmentation degrades aggregate accuracy not by producing wrong answers but by preventing the model from producing any answer at all. Switching to Raw100k --- where \texttt{execute\_phreeqc} returns the simulator output inline and the agent does not have to issue \texttt{read\_file} calls to inspect sections --- drops Gemini Flash 3's median \texttt{read\_file} traffic from \GeminiTOCReadFileMedian{} to \GeminiRawReadFileMedian{} calls per question and lowers step-budget exhaustion from \GeminiTOCMaxStepsBreakdown/200 to \GeminiRawMaxStepsBreakdown/200 (Appendix~\ref{sec:appendix-gemini-step-budget}); this isolates TOC navigation overhead, not PHREEQC operation, as the mechanism behind the below-mid-tier non-commit failure.

\label{sec:diagnostic}

\subsection{External Harness Comparison}

To control for harness quality, we compared our custom agent against vendor-default external CLI harnesses on a random 50-question scenario-spanning subsample (seed 42), with the backbone held fixed within each comparison panel: Claude Sonnet 4.6 against the official Claude Code CLI, and GPT-5.4 against OpenAI Codex CLI. Each harness runs under its native deployed-product defaults; budget configuration, the Codex \texttt{reasoning\_effort} setting, and the per-condition error breakdown are deferred to Appendix~\ref{sec:appendix-external-harness}. Table~\ref{tab:sdk-comparison} reports matched accuracy and per-question input-token cost on the same 50 items.

The accuracy direction is mixed across vendors: custom dominates Sonnet by \SDKCustomTOCMinusSDK{} but trails Codex on GPT-5.4 by 18.0\,pp. The token-efficiency direction is uniform: custom Agent-TOC reaches 2.7--3.3$\times$ more correct answers per input token than the deployed external CLI on both backbones (Sonnet: \SonnetCustomTOCPerCorrectK\,K vs \SDKSonnetPerCorrectK\,K tokens per correct; GPT-5.4: \GPTFiveFourCustomTOCPerCorrectK\,K vs \CodexGPTFiveFourPerCorrectK\,K). Codex's higher absolute accuracy on GPT-5.4 is purchased at 4.1$\times$ the per-question input-token cost; under a fixed-budget setting, custom TOC delivers more correct answers. We read this as evidence that the cost-efficiency advantage of purpose-built scientific agent harnesses is robust to the absolute-accuracy direction.

An agent can solve new questions through grounded computation while also losing questions that the same model answered correctly without tools. Higher retention indicates greater stability under tool augmentation: among questions the model answered correctly without tools, fewer are lost after adding the PHREEQC agent loop.

The completed runs show that simulator access can produce large net gains while still losing some direct-baseline correct answers. The asymmetry is clearest in the loss counts: all five top- and mid-tier TOC agents gain many questions through tool use, but the number of previously correct answers they lose ranges from \SonnetLost{} for Claude Sonnet 4.6 and \OpusLost{} for Claude Opus 4.6 to \GPTFiveTwoLost{} for GPT-5.2 and \GPTFiveOneLost{} for GPT-5.1. Retention therefore acts as a stability diagnostic: it measures whether an agent can exploit PHREEQC without destabilizing answers the same model could already produce without tools. This instability is most visible for the GPT-family agents: GPT-5.4 gains \GPTFiveFourGained{} questions but loses \GPTFiveFourLost{} direct-correct questions, GPT-5.2 gains \GPTFiveTwoGained{} but loses \GPTFiveTwoLost{}, and GPT-5.1 gains \GPTFiveOneGained{} but loses \GPTFiveOneLost{}. Thus the weaker retention is not simply a failure to benefit from PHREEQC; in this harness, it reflects less stable behavior while navigating the tool loop, simulator outputs, and final-answer mapping. The lost-item sets overlap only partially across backbones, so the effect is not explained simply by a fixed set of questions that are intrinsically fragile under tool use; it reflects model- and trajectory-specific failures introduced by the tool loop.

The TOC ablation pattern aligns with model capability tier rather than with vendor. For the three top-tier models in our evaluation (Claude Opus 4.6, Claude Sonnet 4.6, and GPT-5.4), TOC essentially matches raw-output accuracy at large input-token savings: Opus is \OpusTOCMinusRaw{} relative to raw at \OpusTOCTokenReduction{} token reduction, Sonnet is \SonnetTOCMinusRaw{} at \SonnetTOCTokenReduction{}, and GPT-5.4 is \GPTFiveFourTOCMinusRaw{} at \GPTFiveFourTOCTokenReduction{}. For the two mid-tier models in our evaluation (GPT-5.2 and GPT-5.1), TOC is a measurable cost: GPT-5.2 is \GPTFiveTwoTOCMinusRaw{} at \GPTFiveTwoTOCTokenReduction{}, and GPT-5.1 is \GPTFiveOneTOCMinusRaw{} at \GPTFiveOneTOCTokenReduction{}. The cut crosses vendor: GPT-5.4 sits with the Anthropic top-tier rather than with its same-vendor mid-tier siblings, while GPT-5.1 and GPT-5.2 sit on the mid-tier side regardless of being from the same family as GPT-5.4. This pattern is consistent with a capability-mediated mechanism: TOC navigation requires interpreting a table-of-contents structure, issuing precise line-range read calls, extracting the requested numerical quantity, and mapping it to an answer choice. Each step is a capability test; mid-tier models stumble on one or more of these steps and lose accuracy that raw-output access would have preserved by delivering the entire payload upfront. The GPT-5.2 regression sits an order of magnitude outside the model's measured TOC rerun SD of \GPTFiveTwoTOCRerunSD\,pp (Table~\ref{tab:toc-rerun-variance}); the GPT-5.1 regression sits within roughly two of its larger \GPTFiveOneTOCRerunSD\,pp SD but is directionally consistent with the same capability-tier pattern. We therefore read the TOC interface as Pareto-good for top-tier models in this harness --- no measurable accuracy cost at substantial token savings --- and as a measurable tradeoff for mid-tier models, with a mechanism that points to navigation capability rather than vendor or context-window size. Appendix~\ref{sec:appendix-cross-protocol-overlap} quantifies this directly via a cross-protocol right-item overlap analysis: both protocols catch items the other misses for every model, but for mid-tier GPT the asymmetry favors Raw100k by 16--19 net items (raw-only minus TOC-only), while for top-tier Sonnet the two protocols disagree on only 6\% of items and for GPT-5.4 the disagreement is roughly symmetric. Appendix~\ref{sec:appendix-retention-decomp} reports per-bin lost-rate decompositions showing that on the small-output bulk of the benchmark ($\le$50k characters), mid-tier lost rates range from 26\% to 60\% across bins (with $n\ge 15$ direct-right items per cell), while top-tier lost rates stay below 20\% on the same bins. Because \OutputLeHundredK{} of items are not cap-affected, the GPT accuracy losses cannot be attributed to Raw100k truncation; we examine the output-size dependence next.

The aggregate TOC-vs-Raw100k difference also hides systematic variation by output size. Within the \RawCapUnaffectedN{} cap-unaffected items where Raw100k returns the file in full, Sonnet's TOC matches or beats Raw100k across every output-size bin, with the largest TOC advantage in the 20--50k mid-range ($+$3.8pp, $n$=26). GPT-5.4 shows the opposite pattern in the small mode --- TOC is roughly tied with Raw100k on outputs $\le$10k ($n$=82) but better in the 10--20k bin ($+$6.4pp, $n$=47) --- and Raw100k regains an advantage in the long tail at 250--500k ($+$14.3pp, $n$=21). For mid-tier GPT models, Raw100k generally beats TOC on the bulk of items: GPT-5.2 trails TOC by $-$8.0pp aggregate, with bin-level gaps of $-$12.8pp at 10--20k ($n$=47) and $-$11.5pp at 20--50k ($n$=26). The pattern is therefore non-monotone in both output size and model: TOC's structured access is well-utilized by Sonnet across the distribution, weakly utilized by GPT-5.4 except in the long tail, and a net cost for the mid-tier GPT family on the items that dominate the benchmark. Read against the per-model rerun SDs in Table~\ref{tab:toc-rerun-variance}, the GPT-5.2 bin gaps sit an order of magnitude above the model's measured TOC variance and are therefore the most robust quantitative result in this output-access analysis; the GPT-5.4 long-tail gap also exceeds its model SD; the smaller GPT-5.4 and GPT-5.1 small-bin gaps sit closer to noise and should be read as directionally consistent with the broader pattern rather than as standalone effect sizes.

\section{Discussion}

\paragraph{Benchmark-centered diagnostic evaluation.}
The benchmark is designed around a simple premise: tool-augmented scientific agents should be evaluated by more than headline accuracy. The MCQ benchmark provides a scalable grading surface, but the accompanying analyses ask how that accuracy is obtained: whether gains come from grounded execution rather than chain-of-thought alone, whether tools introduce regressions, whether output-access choices change cost and trajectories, and whether residual failures arise from input construction, execution recovery, output navigation, or answer mapping.

\paragraph{PHREEQC as a simulator testbed.}
The benchmark should not be read as a claim that PHREEQC is uniquely important for AI evaluation. Its role is to instantiate a class of tasks where the answer is deterministic but the agent must operate a realistic scientific tool. The single-simulator design lets us instrument failures closely and release complete execution artifacts; it does not establish cross-simulator generalization.

\paragraph{Tool access is an intervention, not a monotone advantage.}
The completed retention analyses show that tool use can add many correct answers while still losing a nontrivial number of direct-baseline correct answers. The decomposition in Appendix~\ref{sec:appendix-retention-decomp} sharpens this: lost rates vary across output-size bins. On the small-output bulk of the benchmark ($\le$50k characters, 170 items), mid-tier GPT lost rates range from 26\% to 60\% across bins, while top-tier lost rates stay below 20\% on the same bins. Larger-output bins have smaller direct-right denominators and therefore noisier per-bin rates that should be read with caution; the qualitative pattern of higher mid-tier loss persists. Tool augmentation under mid-tier capability is therefore systematically converting capability the model already had into errors on the bulk of the benchmark, in the output regimes where TOC navigation is most actively engaged. This is the main evaluation lesson of the benchmark: tool access changes the model's behavior in structured, not random, ways, so item-level movements should be reported in addition to aggregate accuracy whenever an evaluation claims grounded tool use.

\paragraph{Rerun stability and retention are independent properties.}
Our TOC rerun-variance experiment (Appendix~\ref{sec:appendix-stability}, Table~\ref{tab:toc-rerun-variance}) reveals that TOC stability does not track with the retention metric. GPT-5.2 has the lowest retention rate among completed agents (\GPTFiveTwoRetention) but the smallest measured TOC rerun SD (\GPTFiveTwoTOCRerunSD\,pp); GPT-5.1 has higher retention (\GPTFiveOneRetention) but the largest rerun SD (\GPTFiveOneTOCRerunSD\,pp). Retention measures whether tool augmentation preserves direct-mode correct answers at the item level; stability measures whether the same agent run twice on the same items lands on the same accuracy. These are independent failure modes: a model can be reproducible while systematically losing direct-correct items under tool augmentation, and conversely a model can have higher retention while exploring different items across reruns. Most benchmark papers conflate the two under ``noise.'' Reporting them separately exposes structural properties of the agent-protocol pair that aggregate accuracy hides, and we therefore recommend both metrics be reported in future tool-augmented agent evaluations. Appendix~\ref{sec:appendix-stability} makes this concrete on GPT-5.1: a $\GPTFiveOneTOCRerunSD$\,pp aggregate rerun SD corresponds to 59\% of items individually flipping between right and wrong across reruns, with variance concentrated in mid-output-size bins and on truth-B items rather than spread uniformly.

\paragraph{TOC is a mechanism, not the paper identity.}
The metadata-only TOC interface addresses a practical problem in this benchmark: large simulator outputs should not be blindly injected into context. It is a supporting design choice and an ablation, not a standalone claim that TOC is the best possible output-access protocol. Comparisons against LLM summaries, vector retrieval, or hybrid schemes are better studied in a future multi-simulator benchmark where output structure varies across domains.

\paragraph{TOC's effect tracks model capability, not vendor.}
The TOC ablation pattern (Section~\ref{sec:diagnostic}) cuts cleanly along model capability tier and crosses vendor: GPT-5.4 behaves like the Anthropic top-tier (TOC matches raw output at substantial token savings), while GPT-5.1 and GPT-5.2 lose 8--10\,pp under TOC despite being from the same vendor as GPT-5.4. We interpret this as a capability-mediated effect: TOC navigation requires interpreting a structured pointer, issuing precise line-range reads, extracting a numerical quantity, and mapping to an answer choice. Each step is a capability test that mid-tier models can fail; raw-output access papers over these failures by delivering the entire payload upfront. The implication for tool-augmented agent design is that output-access protocol should be matched to the deployed model's capability rather than chosen as a uniform interface across a model fleet. The implication for benchmark design is that any single output protocol can advantage some models over others, so output-access ablation should be reported alongside aggregate accuracy whenever a benchmark involves long simulator outputs. Appendix~\ref{sec:appendix-trajectory} sharpens this further by showing the failure mechanism is itself capability-tier-dependent: top-tier agents fail by step-budget exhaustion after committing, mid-tier agents by early commitment to a wrong answer, and the below-mid Gemini Flash 3 agent by step-budget exhaustion without ever committing; raising the step ceiling helps the first group but not the others.

\paragraph{Why a benchmark contribution matters.}
The intended contribution is reusable measurement infrastructure for scientific agents. The diagnostic moves the benchmark supports include: per-output-bin lost-rate decomposition (Appendix~\ref{sec:appendix-retention-decomp}), which surfaces the structural pattern that aggregate accuracy hides; per-question rerun stability (Appendix~\ref{sec:appendix-stability}), which decomposes a 5.5\,pp aggregate SD into a 59\%-of-items-flipping micro-pattern; per-scenario discriminative-power categorization (Appendix~\ref{sec:appendix-scenario-stratification}), which identifies that roughly four scenarios drive most of the cross-model accuracy gap; and failure-mechanism stratification (Appendix~\ref{sec:appendix-trajectory}), which separates retry-loop failures from early-commit failures and from non-commit exhaustion even when aggregate trajectory medians look identical. These are community-facing diagnostics that are difficult to obtain from static science QA benchmarks, and they generalize beyond geochemistry to any tool-augmented scientific agent setting that involves a simulator with structured outputs.

\paragraph{Broader impacts.}
The positive use case for this benchmark is more reproducible evaluation of scientific agents before they are trusted in real computational workflows. The main risk is over-trust: high aggregate accuracy on multiple-choice simulator tasks should not be read as evidence that an agent can autonomously perform scientific modeling without expert oversight. We therefore release logs and generated simulator artifacts so failures can be inspected rather than hidden behind final-answer scores.

\section{Limitations}

\paragraph{Single simulator.}
The current benchmark uses one simulator and one scientific domain. This is a deliberate instrumentation choice rather than a claim of domain completeness. We do not claim that the measured retention rates, failure proportions, or TOC/raw tradeoffs generalize unchanged to other simulators.

\paragraph{Scenario dependence.}
The benchmark contains \BenchN{} question items but \BenchScenarioN{} scenario stems. We therefore report scenario-level metrics and do not treat every item as an independent scientific scenario.

\paragraph{Multiple-choice format.}
Multiple-choice grading enables controlled, deterministic evaluation but gives models a finite answer set. We use MCQ because it makes the benchmark scalable and reproducible, and because the paper's central question is how to allocate evaluation budget across agent and output-access protocols under a fixed task surface. The results should therefore be interpreted as measurements under this benchmark format rather than as unconstrained scientific modeling performance.

\paragraph{Database dependence.}
The benchmark fixes an author-supplied validated PHREEQC thermodynamic database. Results should be interpreted with that database as part of the task definition. Changing the database can change numerical outputs and should be treated as a different benchmark condition.

\paragraph{Closed-model and API drift.}
LLM APIs can change over time, and stochastic or implementation-level variation can affect exact scores. We release prompts, logs, simulator inputs, outputs, and evaluation scripts so future work can rerun the benchmark under controlled conditions.

\paragraph{Capability-tier sample size is small.}
Our capability-tier interpretation of the TOC ablation (Section~\ref{sec:diagnostic}) rests on three top-tier, two mid-tier, and one below-mid-tier model spanning three vendors. The within-tier consistency is striking, and the cross-vendor placement of GPT-5.4 with the Anthropic top-tier is direct evidence against a vendor-effect explanation; nevertheless, the line between tiers is informal --- based on context window, qualitative capability, and observed direct-baseline accuracy rather than on a formal capability metric --- and additional mid-tier or below-mid-tier agents would strengthen the finding. We did not run an agent condition for Gemini~2.5~Flash because its no-tool baselines alone required 2.3 hours of total wall-clock time under our two-worker API configuration; the Gemini~3~Flash~Preview TOC agent did complete and is reported in Section~\ref{sec:main-results}.

\paragraph{Anthropic agent variance unmeasured.}
The TOC rerun-variance experiment (Appendix~\ref{sec:appendix-stability}, Table~\ref{tab:toc-rerun-variance}) was executed for the GPT family only. The Anthropic Pareto-good interpretation in Section~\ref{sec:diagnostic} therefore relies on the assumption that Opus and Sonnet TOC variance is no larger than the largest measured GPT TOC variance ($\TOCRerunMaxSD$\,pp). This assumption is not directly verified. The Opus and Sonnet headline numbers in Table~\ref{tab:main-results} are single-run measurements and could shift on rerun; the qualitative Anthropic-vs-GPT split would survive moderate Anthropic variance but a stronger version of the claim would require paired Anthropic reruns.

\paragraph{Human calibration.}
The current evaluation compares model and harness conditions, but it does not yet include a human baseline. As a result, task difficulty is calibrated by simulator execution and cross-model behavior rather than by expert time-to-solve or expert accuracy. A small expert pilot would strengthen future versions of the benchmark.

\section{Conclusion}

We introduced \BenchName, a benchmark for evaluating LLM agents that operate deterministic scientific simulators under a unique-answer setting. The benchmark reframes PHREEQC from a narrow domain application into a controlled testbed for studying tool-augmented scientific computation. The central findings, organized around benchmark diagnosis rather than geochemistry, are: tool access produces net gains across the five top- and mid-tier completed agents at variable retention costs (52.7--87.8\%) but regresses below the no-tool baseline on the below-mid Gemini Flash 3 agent; chain-of-thought does not substitute for grounded execution; output-access protocol effects align with model capability tier rather than vendor, with a metadata-guided interface (TOC) acting as a Pareto-good interface for top-tier models and an 8--10\,pp accuracy cost for mid-tier models; rerun stability and item-level retention are independent properties of an agent and should be reported separately; and failure mechanism is itself capability-tier-dependent, with top-tier failures dominated by step-budget exhaustion after committing, mid-tier by premature commitment, and below-mid by step-budget exhaustion without committing. The result is a reusable diagnostic harness for measuring scientific tool-use agents and locating where reliability is lost.

\section{External Harness Comparison: Methodology and Failure Modes}
\label{sec:appendix-external-harness}

This appendix expands on the matched 50-question external-harness comparison (Table~\ref{tab:sdk-comparison}) with full configuration details and per-condition failure-mode breakdowns.

\paragraph{Step budgets and approval policies.}
Each harness is run under the deployed-product defaults of its native CLI: our custom agent uses a 24-step budget; the Claude Code CLI uses a 20-turn budget; the Codex CLI exposes no step-budget flag and is bounded only by a 600\,s subprocess timeout. Approval and sandboxing prompts are disabled in all three so that no human-in-the-loop interaction can occur (\texttt{--dangerously-skip-permissions} for Claude Code, \texttt{--ask-for-approval never} and \texttt{--dangerously-bypass-approvals-and-sandbox} for Codex, no approval gate for the custom agent).

\paragraph{Reasoning-effort confound on the GPT-5.4 panel.}
The Codex CLI is configured with \texttt{model\_reasoning\_effort=medium}; our custom GPT-5.4 condition uses default chat-completion calls without a \texttt{reasoning\_effort} parameter. The GPT-5.4 panel of Table~\ref{tab:sdk-comparison} therefore reflects a reasoning-effort difference in addition to harness design, and the absolute-accuracy gap (Codex \CodexGPTFiveFourAcc{} vs custom Agent-TOC \GPTFiveFourCustomTOCMatchedAcc{}) cannot be cleanly attributed to harness alone. The token-efficiency reading in Table~\ref{tab:sdk-comparison} (custom uses 4.1$\times$ fewer input tokens per question than Codex) is robust to this confound because it directly measures the deployed-product cost.

\paragraph{Claude Code CLI failure breakdown.}
On Sonnet, the Claude Code CLI scored 30/50 with 20 errors. 10 of those 20 are non-commits: \SDKSonnetTimeouts{} subprocess timeouts (the agent ran for the full 600\,s without producing a final-answer message) plus \SDKSonnetMaxTurns{} step-budget exhaustions at 20 turns. The remaining 10 are committed-but-wrong answers. The non-commit pattern mirrors the below-mid-tier non-commit signature observed for Gemini Flash 3 in Section~\ref{sec:main-results} but here on a top-tier model under a different harness, supporting the reading that final-answer commitment under tool augmentation is shaped by harness design as well as model capability.

\paragraph{Codex CLI cost composition.}
Codex's 11.7M total input tokens on the 50-question subsample include 10.5M cached input tokens (89\% cache hit). For raw API-billed cost the cached fraction is roughly half-priced, so the absolute dollar cost of the Codex run was approximately \$18 at GPT-5 standard pricing. Per-question tokens reported in Table~\ref{tab:sdk-comparison} include the cached fraction because the cost-efficiency comparison is in context-load units (input tokens routed through the model) rather than billing units; reporting in billing-units would shift the picture in Codex's favor by roughly $1/3$ but does not change the direction of any tier conclusion.

\subsection{Implications for Benchmark Methodology}

Three implications follow for tool-augmented agent evaluation in general:

\begin{enumerate}[leftmargin=*, itemsep=2pt]
    \item \textbf{Aggregate SD understates the share of variance-prone items.} A 5.5\,pp aggregate SD can correspond to a benchmark in which 59\% of items individually flip between rerun samples. Single-run accuracy on protocol--model pairs at this stability level should be interpreted as an estimate of expected accuracy, not as a property of the model on specific items.
    \item \textbf{Variance is structured by output regime.} Variance-prone items concentrate where the access protocol is most actively engaged; for GPT-5.1 + TOC, that is the mid-output-size band where the model must make non-trivial navigation decisions. This suggests a path for benchmark designers: stratifying analysis by output-size regime exposes structure that aggregate accuracy hides.
    \item \textbf{Stability and capability are not the same property.} Some always-wrong items reflect intrinsic capability limits (especially in the $>$500k bin); some variance-prone items reflect navigation stochasticity. A benchmark that conflates the two under a single accuracy number cannot tell a model developer whether to invest in capability scaling or in interface design. Reporting the per-item-score histogram alongside aggregate accuracy separates these two failure modes.
\end{enumerate}

\end{enumerate}

The mean failed-item step count of 18--19 indicates that even the non-ceiling failures used a substantial fraction of the budget. GPT-5.4 sits between these patterns: failed-item median 10 (slightly above its overall median of 8), with 3.6\% of failures reaching the ceiling. It exhibits more retry behavior than the mid-tier GPT pair but markedly less than the Anthropic agents.

\subsection{What This Adds to the Capability-Tier Reading}

The two failure patterns map onto the capability-tier framing of Section~\ref{sec:diagnostic} in a specific way: top-tier agents under TOC fail by \emph{persistence without success}, while mid-tier GPT agents fail by \emph{premature commitment}. Both fail; both contribute to the headline accuracy gap. But the implication for tool-augmented agent design differs:

\begin{enumerate}[leftmargin=*, itemsep=2pt]
    \item For top-tier agents, raising the step ceiling could in principle recover some retry-loop failures --- but at the cost of substantially higher wall-clock time and token cost on already-failing items.
    \item For mid-tier agents, raising the step ceiling would not help: their failures already commit before the ceiling. Recovering these failures requires interventions that change \emph{how} the agent navigates and commits (better TOC return formats, calibrated abstention, or richer tool feedback), not the budget for retries.
\end{enumerate}

This is a benchmark observation that aggregate trajectory medians cannot surface: identical median step counts across capability tiers conceal qualitatively different failure mechanisms.

\section{Datasheet for \texorpdfstring{\BenchName}{PHREEQC-MCQ-200}}
\label{sec:appendix-datasheet}

This appendix documents the benchmark in the format of \citep{gebru2021datasheets}. We report only properties relevant to evaluation use; full reproducibility material is in the artifact (Section~\ref{sec:appendix-artifact}).

\subsection{Motivation}

\paragraph{Purpose.}
\BenchName{} was created to evaluate tool-augmented LLM agents on a deterministic scientific simulator under a unique-answer setting, with explicit support for retention, output-access ablation, scenario-clustered uncertainty, and failure-mode decomposition. The benchmark is designed as a measurement instrument for compound AI systems, not as a domain assessment of geochemistry.

\paragraph{Funding and authorship.}
The benchmark was authored and reviewed by domain experts in aqueous geochemistry. Authorship and funding details are withheld for double-blind review.

\subsection{Composition}

\paragraph{Instances.}
Each instance is a four-option multiple-choice question with a unique simulator-derived target value, the four answer choices, and a designated correct option ($A$, $B$, $C$, or $D$). The benchmark contains \BenchN{} question items derived from \BenchScenarioN{} validated simulation scenario stems; multiple items may share a scenario stem when the simulation produces multiple distinct quantities (different output fields, time steps, or derived values). The truth-label distribution is A=63 (31.5\%), B=47 (23.5\%), C=48 (24.0\%), D=42 (21.0\%); the majority-label baseline is therefore 31.5\%.

\paragraph{Item content.}
Each item provides natural-language problem text describing a chemical scenario (e.g., dissolution of a mineral in a specified aqueous solution under specified thermodynamic conditions) and asks for a specific computed quantity (pH, saturation index, concentration of a particular species, time-resolved value, etc.). The agent receives the problem text and four answer choices; it does not receive a prewritten PHREEQC input file.

\paragraph{Format.}
JSONL with one item per line. Fields include \texttt{question}, four answer-choice fields, \texttt{answer} (the correct option), and metadata used by the evaluation harness.

\paragraph{Companion files.}
The benchmark is distributed with (i)~the author-supplied PHREEQC thermodynamic database used during item validation and required at evaluation time; (ii)~the agent system prompts (Direct, CoT, TOC, Raw) and tool contracts; (iii)~per-question chat logs and generated PHREEQC artifacts for failure cases; (iv)~scenario-stem groupings; and (v)~the analysis script that regenerates every table in this paper.

\paragraph{Output-size distribution.}
Simulator outputs are heavy-tailed and bimodal: \OutputLeHundredK{} of \texttt{result.out} files are at most 100k characters (95th percentile within this mode at $\sim$55k characters), and the remaining \OutputGtHundredK{} begin at $\sim$369k characters and extend to a maximum of \OutputMaxChars. The empty interval between modes is the rationale for the 100k raw-output cap (Section~\ref{sec:toc}). Output sizes per question are not fixed at dataset construction time but are produced when an agent's PHREEQC input is executed; different agents may produce slightly different output sizes for the same item depending on their input choices.

\subsection{Collection and Validation}

\paragraph{Authoring.}
Items were authored by domain experts in aqueous geochemistry and reviewed by additional independent reviewers.

\paragraph{Validation criteria.}
Each candidate item was retained only if (i)~the simulation setup executes successfully against the frozen author-supplied database, (ii)~the intended answer is uniquely determined from the PHREEQC output, (iii)~the four answer choices are numerically plausible (distractors are not trivially distinguishable from the correct option without simulation), (iv)~the question statement is unambiguous to multiple independent reviewers, and (v)~the answer is not reliably recoverable from parametric knowledge alone --- items that direct no-tool models solved consistently during pilot runs were excluded so that the benchmark isolates tool-grounded computation rather than textbook recall.

\paragraph{Removed items.}
Ambiguous items, duplicated items, and items whose answer depended on display-precision artifacts in PHREEQC's \texttt{result.out} format (i.e., where the correct option and a distractor would round to the same value at PHREEQC's default decimal output) were removed before freezing.

\subsection{Recommended Use}

\paragraph{Evaluation tasks.}
\BenchName{} is designed for: (i)~evaluating tool-augmented agent accuracy and retention under a deterministic, unique-answer scientific computation setting; (ii)~comparing output-access protocols (TOC, raw-output, summary, retrieval) on a benchmark with a controlled simulator; (iii)~studying capability-tier effects in agentic interfaces; and (iv)~surfacing failure-mode decomposition and rerun-stability behavior (Sections~\ref{sec:appendix-stability} and~\ref{sec:appendix-trajectory}).

\paragraph{Not designed for.}
\BenchName{} is not designed to assess open-ended scientific modeling capability, to grade chemistry knowledge under a textbook-style setting, or to support automated benchmark gaming via web-text retrieval (the validation criteria explicitly exclude items recoverable from parametric knowledge).

\paragraph{Grading.}
Grading is exact-match on the predicted answer choice ($A$, $B$, $C$, $D$). Missing, malformed, or unparseable final answers are counted as incorrect; agents must commit to one of the four options.

\paragraph{Versioning.}
The version reported in this paper is the \BenchName{} frozen release. Future revisions may extend or refine items but will be distributed under a distinct version identifier; results in this paper should be interpreted under the frozen release only.

\paragraph{Data integrity.}
Benchmark items were authored by domain experts and have not been distributed publicly prior to release of this paper. We have not conducted a systematic web-leakage audit; the dataset is released alongside this paper and any subsequent leakage audits should be interpreted relative to that release date.

Any post-release corrections will be tracked in the artifact's \texttt{ERRATA.md}. We commit to maintaining the frozen version of this paper's evaluation alongside any subsequent revisions.
